# Cross-Language Test Mapping

A systematic approach to maintaining traceable test coverage between a Python codebase
and its Rust port. Every Python test is tracked through to its Rust equivalent, with CI
enforcement to prevent coverage drift.

This technique was developed during the flowmark port and is generalizable to any
Python-to-Rust porting effort.

See also: [Test Coverage for Porting](../guidelines/test-coverage-for-porting.md),
[Porting Principles and Anti-Patterns](../guidelines/porting-principles-and-antipatterns.md)
(Principle 9: Dynamic Corpus Validation).

## Why Test Mapping Matters

During a port, test count alone is misleading.
A Rust codebase can have 400+ tests while still missing coverage for critical Python
behaviors — if the tests cover different code paths or encode wrong expected values (see
Principle 9). Test mapping provides:

1. **Traceability:** Every Python test maps to one or more Rust equivalents
2. **Gap detection:** Unmapped Python tests are immediately visible
3. **Split tracking:** When a single Python test becomes multiple Rust tests, the
   relationship is explicit
4. **Exclusion justification:** Tests intentionally not ported are documented with
   reasons
5. **CI enforcement:** The mapping is validated on every push — no silent drift

## Architecture

The system uses three YAML manifest files and a CLI tool for discovery and validation.

```
admin/port-coverage-mapping/
├── python-tests.yaml       # All Python tests (auto-discovered)
├── rust-tests.yaml         # All Rust tests (auto-discovered)
└── test-mapping.yaml       # Python → Rust mappings (auto-generated, manually curated)
```

### Data Flow

```
Python repo                              Rust repo
tests/test_*.py                          tests/test_*.rs + src/**/tests
      │                                        │
      ▼                                        ▼
discover-python                          discover-rust
(AST parsing)                            (cargo test --list)
      │                                        │
      ▼                                        ▼
python-tests.yaml                        rust-tests.yaml
      │                                        │
      └──────────┐          ┌──────────────────┘
                 ▼          ▼
              test-mapping.yaml
              (Python → Rust links)
                      │
                      ▼
              check-mapping (CI)
              (validates completeness)
```

## YAML Schemas

### python-tests.yaml

Auto-generated by scanning Python test files with AST parsing:

```yaml
- file: tests/test_alerts.py
  function: test_alert_after_heading
  class_name: null              # Only for class-based tests
  test_type: integration        # unit | integration | golden | infrastructure
  line_number: 245
  doc_string: Test alert immediately after a heading.
```

**Test type classification** (heuristic, configurable):
- `unit` — isolated function tests
- `integration` — tests that call through the main processing pipeline
- `golden` — reference document / snapshot tests
- `infrastructure` — CLI, config, file resolution, skill tests

### rust-tests.yaml

Auto-generated by running `cargo test -- --list --format terse`:

```yaml
- file: tests/test_alerts.rs
  function: test_alert_after_heading
  line_number: 140
```

Rust tests are simpler: no class hierarchy, no type classification needed.

### test-mapping.yaml

The core mapping file.
Auto-generated skeleton, manually curated:

```yaml
- python_file: tests/test_alerts.py
  python_function: test_alert_after_heading
  python_class: null
  status: mapped
  rust_file: tests/test_alerts.rs
  rust_function: test_alert_after_heading
  rust_functions: []
  notes: null
```

**Status values:**

| Status | Meaning | Action Required |
| --- | --- | --- |
| `mapped` | Python test has Rust equivalent(s) | None — parity achieved |
| `partial` | Python test split into multiple Rust tests | `rust_functions` lists all parts |
| `excluded` | Intentionally not ported | `notes` must explain why |
| `missing` | Not yet ported | Must be resolved before completion |

### Partial Mapping Example

When a single Python test with many assertions is split into focused Rust tests:

```yaml
- python_file: tests/test_ellipses.py
  python_function: test_ellipses
  status: partial
  rust_file: tests/test_ellipses.rs
  rust_function: null
  rust_functions:
  - test_ellipses_basic_conversions
  - test_ellipses_at_boundaries
  - test_ellipses_multiple
  - test_ellipses_punctuation
  - test_ellipses_does_not_apply
  - test_ellipses_multiline
  - test_ellipses_edge_cases
  - test_ellipses_code_like
  - test_ellipses_four_dots
  - test_ellipses_quotes
  notes: >-
    Python single function with ~98 assertions was split into 10 Rust
    functions covering all assertion groups
```

## CLI Tool

The discovery and validation commands are implemented as a Python CLI tool
(`flowmark-dev` in the flowmark port).
Adapt the tool name and paths to your project.

### Commands

```bash
# Discover Python tests
flowmark-dev discover-python \
  --repo-url https://github.com/org/project \
  --ref v0.6.4 \
  --output admin/port-coverage-mapping/python-tests.yaml

# Discover Rust tests
flowmark-dev discover-rust \
  --project-dir . \
  --output admin/port-coverage-mapping/rust-tests.yaml

# Initialize mapping from Python tests (preserves manual edits)
flowmark-dev init-mapping \
  --python-yaml admin/port-coverage-mapping/python-tests.yaml \
  --output admin/port-coverage-mapping/test-mapping.yaml

# Validate mapping completeness (used in CI)
flowmark-dev check-mapping \
  --python-yaml admin/port-coverage-mapping/python-tests.yaml \
  --rust-yaml admin/port-coverage-mapping/rust-tests.yaml \
  --mapping-yaml admin/port-coverage-mapping/test-mapping.yaml
```

### Discovery Implementation Notes

**Python discovery** uses AST parsing (`ast.parse`) to walk `tests/test_*.py` files,
extract function names starting with `test_`, classify by test type based on function
calls and filename patterns, and capture the first line of any docstring.

**Rust discovery** prefers `cargo test -- --list --format terse` for
compiler-authoritative results.
This finds both integration tests (`tests/`) and unit tests (`src/**/mod tests`). A
regex fallback parses `#[test]` attributes directly when cargo is unavailable.

### Regeneration Safety

All three YAML files have an `# Auto-generated.
Manual edits are preserved on re-generation.` header.
The init-mapping command merges new Python tests into the existing mapping file without
overwriting manually curated fields (`status`, `rust_file`, `rust_function`,
`rust_functions`, `notes`).

## CI Enforcement

### GitHub Actions Job

```yaml
check-mapping:
  name: Test mapping check
  runs-on: ubuntu-latest
  needs: test  # Only run after tests pass
  steps:
    - uses: actions/checkout@v7
    - uses: astral-sh/setup-uv@v9
    - name: Install dev tools
      working-directory: python
      run: uv sync --group dev
    - name: Check mapping completeness
      working-directory: python
      run: uv run flowmark-dev check-mapping
```

### Validation Rules

The `check-mapping` command validates:

1. **Every Python test has a mapping entry.** Unmapped tests fail CI.
2. **Every mapped Rust reference exists.** Broken `rust_file`/`rust_function` refs fail
   CI.
3. **No stale entries.** Mapping entries referencing removed Python tests are flagged.
4. **Extra Rust tests are reported** (informational, not a failure — Rust can have
   additional tests beyond what Python covers).

### Report Output

```
=== Test Mapping Coverage Report ===

Python tests:  292
  Mapped:      275
  Excluded:     12
  Partial:       5
  Missing:       0

PASS: All Python tests are covered by the mapping.
```

## Workflow

### During Initial Port

1. Run `discover-python` to generate the Python manifest
2. Run `init-mapping` to create the mapping skeleton (all entries start as `missing`)
3. As you port each module, update entries to `mapped` with Rust references
4. For tests you split, use `partial` with `rust_functions` list
5. For tests you intentionally skip, use `excluded` with explanatory `notes`
6. Run `check-mapping` locally before each PR

### During Ongoing Sync

1. When Python adds new tests, re-run `discover-python` and `init-mapping`
2. New tests appear as `missing` — port them and update to `mapped`
3. Run `discover-rust` to refresh the Rust manifest after adding tests
4. CI prevents merging with unmapped tests
5. **Update smoke-test count constants.** If the project pins manifest sizes (e.g.
   `EXPECTED_PYTHON_TEST_COUNT`, `EXPECTED_RUST_TEST_COUNT`, `EXPECTED_MAPPING_COUNT` in
   a `test_smoke.py`-style guard), bump them to match the new YAML sizes.
   These constants drift on every sync; the failing assertion is telling you to update
   the count, not flagging a parity issue.

### Mapping new test files (not just new tests inside existing files)

When upstream adds an entirely new test file (e.g. `tests/test_cli_help.py`) the mapping
needs a corresponding Rust file decision:

- **Port to a parallel Rust file** of the same name (`tests/test_cli_help.rs`) if the
  test concept maps cleanly.
  Set `status: mapped` for each new entry with `rust_file` pointing at the new file.
- **Mark `excluded` with rationale** if the new test file is Python-specific (e.g.
  packaging-entrypoint tests asserting `[project.scripts]` shape; the Rust analog might
  exist as a `[[bin]]` shape test that isn’t 1:1).
- **Split via `partial`** if the Python test maps to multiple Rust tests.

### When Refactoring Rust Tests

1. Rename or reorganize Rust tests freely
2. Re-run `discover-rust` to update the Rust manifest
3. Update `rust_file`/`rust_function` references in test-mapping.yaml
4. CI validates all references still resolve

## Adapting to Your Project

To implement this system for a new port:

1. **Create the CLI tool** with four commands: `discover-python`, `discover-rust`,
   `init-mapping`, `check-mapping`
2. **Define your test type taxonomy** (unit/integration/golden or whatever fits)
3. **Choose your mapping directory** (e.g., `admin/port-coverage-mapping/`)
4. **Add the CI job** after your test job, with a hard failure on unmapped tests
5. **Version-control all three YAML files** — they are the source of truth for coverage

The key design decision: **mapping is a hard CI gate, not an advisory report.** This
ensures test coverage never silently regresses.
Every new Python test must be mapped before the next PR merges.
