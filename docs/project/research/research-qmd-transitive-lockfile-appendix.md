# Research Appendix: qmd Lockfile Transitive Dependency Plan

## Scope

This appendix covers lockfile-level dependency planning for `qmd` (v2.5.2) beyond direct
manifest dependencies, using `attic/qmd/pnpm-lock.yaml`.

> Basis note: the original snapshot used `attic/qmd/bun.lock`. This refresh uses
> `pnpm-lock.yaml` (now present in the repo) so qmd and tbd share one extraction method
> and one reproducible script. Absolute counts are therefore not directly comparable to
> the bun.lock snapshot, but the structural conclusions hold.

## Extraction Method

Generated by `docs/project/research/data/extract_lockfile_inventory.py` over the pnpm v9
lockfile (see the tbd appendix for the full method). In short: read direct roots from
`importers`, traverse the `snapshots` graph via `dependencies`/`optionalDependencies`
(resolving alias edges), and record one row per lock entry with owner roots and action
classification.

```sh
git clone https://github.com/tobi/qmd.git attic/qmd
git -C attic/qmd checkout 443760f4d5a17550d77a0e3146b5b8f08452991f
uv --no-config run --locked \
  --script docs/project/research/data/extract_lockfile_inventory.py \
  attic/qmd/pnpm-lock.yaml qmd docs/project/research/data/qmd-lockfile
git diff --exit-code -- docs/project/research/data/qmd-lockfile-*
```

The adjacent `extract_lockfile_inventory.py.lock` pins the script’s PyYAML dependency.
The source commit pins the analyzed `pnpm-lock.yaml`; `attic/` is intentionally ignored
so third-party checkouts do not become part of this repository.

In the pnpm lockfile the `typescript` peer is listed under importer `dependencies`, so it
is grouped as runtime here rather than as a separate `peer` group.

Interpretation:
- The transitive graph is still dominated by the LLM runtime (`node-llama-cpp`, now ~129
  of 376 entries) and the MCP server stack, so those spikes remain the highest leverage
  for risk reduction. (Under the original bun.lock basis `node-llama-cpp` alone owned
  226 of 431; the smaller share here reflects the pnpm basis, not a dependency removal.)
- Runtime-owned entries dominate tooling-only entries (`replace-through-runtime-owner` is
  251 vs `removed-with-js-toolchain` 100), so runtime parity testing is the critical path.
- The new Tree-sitter grammar crates own only a handful of transitive entries each and
  map to native Rust crates, so they add little transitive risk.

## Lockfile Alias Note

The earlier alias mismatch (manifest `sqlite-vec-win32-x64` vs lock key
`sqlite-vec-windows-x64`) no longer applies: the current manifest lists
`sqlite-vec-windows-x64` directly, matching the lock key.

## Rust Porting Use Rules

1. For every row marked `replace-through-runtime-owner`, ensure the owner direct
   dependency has a concrete Rust mapping and integration test in the qmd dependency
   port plan.
2. For every row marked `removed-with-js-toolchain`, remove the owning TS/Node
   workflow and verify no runtime command path still references it.
3. For every row marked `split-runtime-and-tooling`, add targeted tests to guard
   runtime behavior while pruning tooling dependencies.
